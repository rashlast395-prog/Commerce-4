# Assumptions Log

Decisions made without explicit sign-off, so they're traceable and revisable.

| # | Area | Assumption | Status |
|---|---|---|---|
| 1 | Delivery fee | Flat platform default fee (`DEFAULT_DELIVERY_FEE_MINOR_UNITS`, GHS 10.00), with an optional per-restaurant override (`deliveryFeeOverride`). Distance-based pricing deferred. | **Implemented** Phase 2 |
| 2 | Menu modifiers | The `modifiers` structure (name + options[] + priceDelta + required) is used for pricing and required-selection validation. | **Implemented** Phase 2 |
| 3 | Cart scope | One restaurant per order — adding an item from a different restaurant prompts to clear the existing cart rather than silently mixing carts. | **Implemented** Phase 2 |
| 4 | Role bootstrap | New Firebase Auth users default to role `customer` via a backend `/auth/bootstrap` call after first sign-in; role upgrades are admin-assigned, not self-service. | Implemented Phase 1 |
| 5 | Delivery address input | Checkout collects a text address (line1 + city) but hardcodes the delivery geopoint to central Accra rather than a real map picker — no maps SDK is in the stated tech stack. Real lat/lng capture (browser geolocation or a map picker) is a follow-up, not yet built. | **Open** — flag if wanted before Phase 5 |
| 6 | Modifier picker UI | Menu items with *required* modifiers can't be added to cart yet from the food card's single "Add to cart" button (shows an alert instead) — needs a modifier-selection modal. Items with no required modifiers work end-to-end. | **Open** — next iteration |
| 7 | Order → payment | Checkout creates a real order (`status: "placed"`, `paymentStatus: "pending"`) but nothing advances it to `payment_confirmed` yet — that transition is wired to the Paystack/Flutterwave webhook in Phase 5. | Expected, by design |
| 8 | Owner picks up multiple restaurants | `restaurant_owner` accounts support multiple `restaurantIds`, but the owner dashboard only manages `restaurantIds[0]` — no location-switcher UI yet. | **Open** — flag if you need multi-location owners now |
| 9 | User/restaurant onboarding | Platform admin assigns roles and creates restaurants by pasting a raw Firebase UID (no user directory/search UI exists yet) — functional but rough. | **Open** — a user picker is a natural follow-up |
| 10 | Rider job claiming | First rider to call accept "wins" the order (Firestore read-then-write, not a transaction) — fine at low volume, but a race condition under real concurrent load. | **Open** — should become a Firestore transaction before production traffic |
| 11 | Payment gateways | Real Paystack/Flutterwave integration code exists (init transaction, webhook signature verification, order reconciliation) but has never been called live — no network path to their APIs from the dev sandbox, and no real keys were provided. When neither is configured, checkout uses a dev-only mock-complete endpoint (disabled if `NODE_ENV=production`) so the order flow is still testable end to end. | **Untested against live APIs** — verify with real sandbox keys before launch |
| 12 | Messaging scope | Conversations are generic (`participantIds` + optional `orderId`), with a REST + WebSocket API fully built on the backend. No chat UI was built in any of the three frontends — `POST /conversations`, `GET/:id/messages` exist and work, but nobody's calling them from a screen yet. | **Backend only** — frontend chat UI is a follow-up |
| 13 | Reservations UI | Customer-web has a reservations page (book + view mine); restaurant owner dashboard has no reservations tab yet (backend route `GET /reservations/restaurant/:id` exists and works, just isn't wired to a UI). | **Partially open** — owner-side reservation management UI is a follow-up |
| 14 | AI analytics scope | Revenue trends, top-selling items, next-day demand forecast (linear regression), and customer segmentation (k-means) are real, unit-tested logic (`services/ai-service/tests/`) — but only verified against synthetic data, never live Firestore, since the sandbox has no network path to a live Firebase project either. Backend proxies these at `/analytics/*` (platform_admin only) — no admin-web UI consumes them yet. | **Logic verified, live data untested, no dashboard UI** |
| 15 | Inventory management | Not built. It was in the original feature list but wasn't prioritized in the Phase 5-9 push — no `inventory` collection reads/writes exist despite being in `DATA_MODEL.md`. | **Not built** |
| 16 | PWA scope | `vite-plugin-pwa` is wired into customer-web only (manifest + service worker generate correctly on build) — admin-web and rider-web don't have PWA support yet. | **customer-web only** |
| 17 | Deployment | Dockerfiles exist for backend and ai-service; `infra/docker-compose.yml` wires them together. Neither has been built/run as a container in this sandbox (Docker itself isn't available here) — only `npx tsx`/`uvicorn` directly. CI workflow (`.github/workflows/ci.yml`) runs typecheck/test/build on every push but has never actually executed (no GitHub repo connected yet). | **Untested — verify `docker compose up --build` and the CI run yourself** |
